# AGENTS.md

## Область действия

Эти правила действуют для всего репозитория AIMETON Site Auditor и обязательны для любого человека или AI-агента, который исследует, проектирует, планирует, реализует, проверяет или сопровождает проект.

## Непрерывная синхронизация образа проекта

Каждое принятое решение, существенное уточнение, обнаруженное ограничение или изменение направления MUST быть внесено в соответствующую документацию независимо от фазы, на которой оно возникло: исследование, планирование, проектирование, разработка, тестирование, приёмка, эксплуатация или разбор инцидента.

Чат, устное обсуждение, комментарий, Issue или Pull Request сами по себе не являются достаточной фиксацией, если решение изменяет архитектурный, плановый или фактический образ проекта.

### Перед началом работы

1. Прочитать относящиеся к задаче материалы в `docs/architecture/`, `docs/roadmap/`, `docs/governance/`, `docs/research/`, `docs/baseline/`, `docs/incidents/`, а также связанные Issues и Pull Requests.
2. Установить действительное состояние, требуемое состояние и ранее принятые ограничения.
3. Не начинать реализацию на основании только последнего сообщения или отдельной Issue, если она расходится с нормативными источниками.

### При возникновении решения или уточнения

Обновить все затронутые источники истины:

| Изменение | Место фиксации |
|---|---|
| Архитектурный принцип, контракт, инвариант или компромисс | `docs/architecture/` и/или ADR; при общеархитектурном значении — `aimeton-architecture` |
| Целевое состояние, этапность, приоритет или зависимость | `docs/roadmap/` и GitHub Project/Issue |
| Фактически реализованное поведение и ограничение | профильная техническая документация, `CURRENT_STATUS.md`, baseline или incident note |
| Проверенный результат, метрика или доказательство | тесты, validation evidence и связанная документация |
| Исследовательская гипотеза, ещё не ставшая решением | `docs/research/` с явным статусом гипотезы |
| Изменение навигации или состава документов | `docs/README.md` и при необходимости корневой `README.md` |

### Межрепозиторная синхронизация AIMETON

1. `aimeton-architecture` хранит нормативный общесистемный и плановый образ AIMETON.
2. AIMETON Site Auditor хранит фактическое поведение коммерческого поискового контура, локальные контракты, ограничения реализации и evidence.
3. `aimeton-infrastructure` хранит фактический образ развёртывания, окружений, жизненного цикла, эксплуатационных контрактов и инфраструктурных рисков.
4. `aimeton-test-sentinel` хранит независимые критерии, сценарии и evidence приёмки; он не должен объявлять подтверждённым то, чего фактически не проверял.
5. `aimeton-mcp-infra` хранит конфигурацию и эксплуатационный контракт собственных MCP-серверов AIMETON.
6. Если решение затрагивает несколько репозиториев, обновления должны быть связаны ссылками на Issues, PR, commits, ADR или evidence. Локальный коммит без отражения межрепозиторного последствия не завершает работу.
7. Плановое изменение в одном репозитории не должно описываться как уже реализованное в другом. Факт подтверждается кодом, конфигурацией, развёртыванием и/или независимым evidence.

### Обязательные различия

Документация MUST явно различать:

- принятое решение и рассматриваемую гипотезу;
- целевое/плановое состояние и фактическое состояние;
- реализованное и только запланированное;
- подтверждённый результат и ожидание;
- действующее решение и отменённое/заменённое решение.

История не переписывается задним числом: изменение фиксируется датой, основанием и ссылкой на Issue, PR, тест, ADR или другое evidence.

### Защита плановых дат и временной структуры GitHub Project

1. Уже заполненные `Start date` и `Target date`, а также их совместимые зеркала `Planned start` и `Planned finish`, являются защищённым состоянием проекта. Коррекция roadmap не должна очищать, неявно заменять или переносить эти значения.
2. Перед массовой синхронизацией, изменением схемы Project, полей дат, Roadmap views или календаря задач MUST быть выполнены чтение затрагиваемых карточек, snapshot исходных значений и project-wide dry-run.
3. Коррекция плана изменяет даты только у явно перечисленных задач. Для каждой такой задачи фиксируются прежнее значение, новое значение и основание. Новые задачи получают даты отдельно; неизменяемые задачи сохраняют введённые даты.
4. Канонические плановые поля — `Start date` и `Target date`. Нельзя создавать дублирующую или заменяющую пару полей без явной миграции значений, настройки представлений и документированного основания.
5. Любое расхождение между каноническими полями, зеркалами, Issue и утверждённым планом останавливает операцию fail-closed до первой записи. Автоматический выбор одной из конфликтующих дат запрещён.
6. Apply разрешён только после dry-run без конфликтов. После apply обязательны read-back всех затронутых значений и повторный dry-run, который должен показать нулевую дельту.
7. Изменение Roadmap view не считается завершённым без проверки временной раскладки. Если API не позволяет подтвердить отображение, создаётся или сохраняется открытая governance Issue до визуального подтверждения владельцем проекта.
8. Обычная lifecycle-синхронизация может изменять только предусмотренные ею поля статуса и фактических дат. Плановые даты изменяются лишь отдельной явно вызванной операцией планирования или миграции.

Подробный исполнимый порядок определён в `docs/governance/GITHUB_PROJECT_ROADMAP.md`.

### Обязательный порядок работы с GitHub

1. Основной канал — доступный встроенный GitHub-коннектор/API.
2. Если нужная операция отсутствует, ограничена или возвращает неполные данные, агент MUST до обращения к пользователю проверить собственный GitHub MCP AIMETON, описанный в `Dimar4713/aimeton-mcp-infra`.
3. Установленный порядок обхода: встроенный GitHub-коннектор → GitHub MCP AIMETON → GitHub REST/GraphQL или `gh` через доверенный серверный контур → ручное действие пользователя.
4. Нельзя просить пользователя выполнять UI-действие, пока не проверены доступные машинные каналы.
5. MCP endpoint и способ авторизации считаются инфраструктурной конфигурацией. Секреты, PAT и bearer-токены запрещено фиксировать в репозитории, логах, evidence или сообщениях.
6. Передача GitHub PAT по незашифрованному HTTP запрещена. До применения удалённого MCP для привилегированных операций MUST быть подтверждён HTTPS/TLS либо защищённый приватный туннель.

### Обязательный порядок диагностики GitHub Actions

1. При сообщении о красном, зависшем или подозрительном GitHub Actions run агент MUST сначала самостоятельно получить фактические данные запуска, а не просить пользователя пересказывать интерфейс.
2. Если известен `run_id` из URL, обязательная цепочка диагностики: `run_id → jobs → failing job_id → job steps → full job logs`; при необходимости дополнительно читаются artifacts и повторные attempts.
3. Для этой цепочки MUST использоваться доступные обходные средства GitHub API/коннектора, включая `fetch_workflow_run_jobs`, `fetch_workflow_job_steps`, `fetch_workflow_job_logs` и `fetch_workflow_run_artifacts`, даже если общий список workflow runs данным коннектором не поддерживается.
4. Если `run_id` неизвестен, агент MUST сначала попытаться получить его через доступные источники: PR checks, commit workflow runs, `gh`, GitHub REST/GraphQL API, собственный GitHub MCP AIMETON, связанные deployment/evidence записи или уже известные ссылки в контексте.
5. Просить пользователя прислать ссылку или номер запуска разрешено только после документированной попытки доступных способов обнаружения. Нельзя объявлять коннектор неспособным читать Actions целиком, если конкретный run доступен по `run_id`.
6. Диагноз MUST опираться на точную failing step и подтверждающий фрагмент лога. До чтения лога нельзя выдавать предположение за установленную причину.
7. После исправления MUST быть выполнены повторная проверка нового run, чтение результата и фиксация фактического состояния; зелёный PR CI не заменяет live/deployment smoke, если задача касается stage или production.

## Continuous Mission Protocol

Канонический стандарт AIMETON: `Dimar4713/aimeton-architecture/docs/governance/CONTINUOUS_MISSION_PROTOCOL.md`.

1. Завершение одного действия, PR, merge, CI или теста не является завершением миссии.
2. После каждого действия агент MUST проверить результат, определить следующий критический безопасный шаг и немедленно выполнить его при отсутствии объективного блокера.
3. Отсутствие нового сообщения пользователя не является блокером.
4. Перед итоговым ответом или завершением tool-сессии обязателен STOP-CHECK:

```text
Есть безопасный однозначный следующий шаг?
├─ Да → выполнить его до итогового отчёта.
└─ Нет → зафиксировать точный объективный блокер или доказанное завершение миссии.
```

5. Фраза «продолжаю» без фактического действия является нарушением контракта.
6. Агент поддерживает очередь из трёх шагов: текущий, следующий и следующий после него.
7. Канонический durable handoff этого репозитория — Issue #173.
8. Каждый существенный комментарий в #173 MUST начинаться с якоря Mission Inertia.

## Motor State

Агент MUST удерживать причинную вертикаль:

```text
сверхзадача AIMETON
→ текущая миссия Site Auditor
→ активный критический путь
→ ближайший безопасный шаг
```

Операционная миссия Site Auditor:

> Превратить Site Auditor из демонстрации в наблюдаемый, объяснимый и качественный коммерческий инструмент, который действительно находит внешние данные, восстанавливает профиль компании и показывает доказуемые AI-возможности для клиента.

Перед итоговым ответом или завершением tool-сессии обязателен MOTOR-CHECK:

```text
Сверхзадача:
Миссия:
Критический путь:
Ближайший безопасный шаг:
```

Если связь текущего действия со сверхзадачей и миссией потеряна, агент MUST сначала восстановить её. Если связь сохранена и безопасный следующий шаг существует, остановка является нарушением контракта.

Канонический якорь:

> Удерживай сверхзадачу. Сохраняй моторное состояние. Не завершай движение в локальной победе.

Каждый существенный комментарий в #173 MUST начинаться с:

```text
MISSION INERTIA
Absence of a new user message is not a blocker.
STOP-CHECK: if a safe next step exists, execute it; otherwise record the exact blocker.
MOTOR-CHECK:
Supergoal:
Mission:
Critical path:
Next safe action:
```

### Перед завершением работы

1. Выполнить MOTOR-CHECK и STOP-CHECK.
2. Проверить, изменился ли архитектурный, плановый или фактический образ проекта.
3. Обновить соответствующие документы в том же PR/коммите. Если это объективно невозможно, создать связанную блокирующую Issue и не объявлять работу полностью завершённой.
4. Проверить согласованность документации, roadmap, Project, Issues, кода, тестов и наблюдаемого результата.
5. В итоговом сообщении перечислить, какие записи актуализированы и какие расхождения остаются.

## Нормативный принцип

> Фактический развивающийся и плановый образ проекта должен непрерывно проявляться в соответствующих записях в соответствующих местах. Решение, оставшееся только в разговоре или локальном контексте исполнителя, считается не интегрированным в проект.
