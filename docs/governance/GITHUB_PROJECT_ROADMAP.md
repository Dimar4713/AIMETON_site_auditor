# GitHub Project Roadmap: плановые и фактические даты

## Назначение

Эта политика разделяет исходный план и фактическое исполнение задач AIMETON.
Roadmap не должен выдавать дату создания Issue или дату коммита за начало
работы.

## Канонические поля

| Поле | Значение | Источник |
|---|---|---|
| `Planned start` | утверждённое плановое начало | ручное планирование |
| `Planned finish` | утверждённое плановое завершение | ручное планирование |
| `Actual start` | дата первого перехода в `In Progress` | automation |
| `Actual finish` | дата первого принятого события завершения | automation |

Project V2 Date хранит календарную дату без времени суток. Исходный timestamp
события остаётся в timeline Issue/PR и в журнале GitHub Actions.

## Неизменяемость фактических дат

- `Actual start` заполняется только один раз — при первом переходе в
  `In Progress`.
- Выход из `In Progress`, блокировка и повторный вход не перезаписывают дату.
- `Actual finish` заполняется только один раз.
- Повторный запуск workflow не меняет уже существующие фактические даты.
- Если `Actual finish < Actual start`, синхронизация завершается ошибкой и не
  записывает противоречивую дату.

## Принятые события завершения

| Объект | Событие | `Actual finish` |
|---|---|---|
| Issue | Issue закрыт | `closed_at` |
| PR | PR объединён | `merged_at` |
| PR | PR закрыт без merge | не заполняется |
| Ручная установка `Done` | только изменение статуса | не заполняется |

Закрытие Issue и merge PR — независимые факты. Если PR закрывает связанный
Issue, каждый объект получает собственную дату по собственному событию.

## Идемпотентная настройка Project

`Project Status Sync` проверяет и при необходимости создаёт:

- четыре Date-поля из таблицы выше;
- `Executive Roadmap`;
- `Actual Delivery`;
- `Active Execution`.

Если поле с каноническим именем уже существует, но имеет другой тип, workflow
работает fail-closed. Если представление с каноническим именем имеет не
Roadmap layout, workflow также не изменяет его автоматически.

Для безопасной проверки предусмотрен ручной запуск:

1. `operation = ensure_schema`;
2. `dry_run = true`;
3. проверить журнал ожидаемых изменений;
4. повторить с `dry_run = false`.

## Представления

| Представление | Начало | Завершение | Фильтр |
|---|---|---|---|
| `Executive Roadmap` | `Planned start` | `Planned finish` | все элементы |
| `Actual Delivery` | `Actual start` | `Actual finish` | все элементы |
| `Active Execution` | `Actual start` | `Planned finish` | без `Done` |

GitHub API создаёт и именует Roadmap views, однако текущий публичный API не
предоставляет параметров для назначения конкретной пары date fields. Поэтому
после первого успешного `ensure_schema` владелец проекта один раз выбирает
пары полей из таблицы в настройках каждого Roadmap view. Это не влияет на
автоматическую фиксацию фактических дат.

## Граница этапов

- Этап A: live-поля, новые фактические события, dry-run, представления.
- Этап B: отдельный dry-run исторического восстановления после `ATS-09B`.
- Этап A не придумывает плановые даты задним числом и не выполняет
  исторический backfill.
