# GitHub Project Roadmap: плановые и фактические даты

## Назначение

Эта политика разделяет исходный план и фактическое исполнение задач AIMETON.
Roadmap не должен выдавать дату создания Issue или дату коммита за начало
работы.

## Канонические поля

| Поле | Значение | Источник |
|---|---|---|
| `Start date` | утверждённое плановое начало | ручное планирование / Issue |
| `Target date` | утверждённое плановое завершение | ручное планирование / Issue |
| `Planned start` | зеркало `Start date` для совместимости новых Roadmap views | automation |
| `Planned finish` | зеркало `Target date` для совместимости новых Roadmap views | automation |
| `Actual start` | дата первого перехода в `In Progress` | automation |
| `Actual finish` | дата первого принятого события завершения | automation |

Project V2 Date хранит календарную дату без времени суток. Исходный timestamp
события остаётся в timeline Issue/PR и в журнале GitHub Actions.

## Неизменяемость фактических дат

- `Actual start` заполняется только один раз — при первом переходе в
  `In Progress`.
- Выход из `In Progress`, блокировка и повторный вход не перезаписывают дату.
- `Actual finish` заполняется только один раз.
- Повторный запуск workflow не меняет уже существующие фактические даты.
- Если `Actual finish < Actual start`, синхронизация завершается ошибкой и не
  записывает противоречивую дату.

## Принятые события завершения

| Объект | Событие | `Actual finish` |
|---|---|---|
| Issue | Issue закрыт | `closed_at` |
| PR | PR объединён | `merged_at` |
| PR | PR закрыт без merge | не заполняется |
| Ручная установка `Done` | только изменение статуса | не заполняется |

Закрытие Issue и merge PR — независимые факты. Если PR закрывает связанный
Issue, каждый объект получает собственную дату по собственному событию.

## Идемпотентная настройка Project

`Project Status Sync` проверяет и при необходимости создаёт:

- Date-поля из таблицы выше;
- `Executive Roadmap`;
- `Actual Delivery`;
- `Active Execution`.

Если поле с каноническим именем уже существует, но имеет другой тип, workflow
работает fail-closed. Если представление с каноническим именем имеет не
Roadmap layout, workflow также не изменяет его автоматически.

Для безопасной проверки предусмотрен ручной запуск:

1. `operation = ensure_schema`;
2. `dry_run = true`;
3. проверить журнал ожидаемых изменений;
4. повторить с `dry_run = false`.

## Представления

| Представление | Начало | Завершение | Фильтр |
|---|---|---|---|
| `Executive Roadmap` | `Start date` или его зеркало `Planned start` | `Target date` или его зеркало `Planned finish` | все элементы |
| `Actual Delivery` | `Actual start` | `Actual finish` | все элементы |
| `Active Execution` | `Actual start` | `Target date` или `Planned finish` | без `Done` |

GitHub API создаёт и именует Roadmap views, однако текущий публичный API не
предоставляет параметров для назначения конкретной пары date fields. Поэтому
после первого успешного `ensure_schema` владелец проекта один раз выбирает
пары полей из таблицы в настройках каждого Roadmap view. Плановые пары
зеркалируются, поэтому старое и новое представления показывают один график.
Это не влияет на автоматическую фиксацию фактических дат.

## Восстановление после рассинхронизации 29–30 июля 2026

Изменение GOV-ROADMAP-01A создало `Planned start`/`Planned finish` поверх уже
действовавших `Start date`/`Target date`, но не перенесло значения. В
результате новые Roadmap views получили пустую временную ось и визуально
сложили карточки в одну вертикаль.

Операция `repair_roadmap`:

1. читает все элементы Project до любой записи;
2. копирует существующую дату в пустое поле второй плановой пары;
3. для Search Recovery `#80–#90` использует утверждённые окна из Issues;
4. не перезаписывает непустую дату;
5. при любом расхождении между двумя парами и Issue работает fail-closed и
   не записывает ничего;
6. поддерживает `dry_run`.

Триггер `project:audit-roadmap` выполняет только dry-run. Триггер
`project:repair-roadmap` применяет проверенный план восстановления.

## Обязательный шлюз изменения плановых дат

Любая будущая корректировка плана, массовое добавление задач, изменение
Date-полей или Roadmap views выполняется только в порядке:

```text
read + snapshot
→ project-wide dry-run
→ conflict gate
→ explicit apply
→ read-back
→ repeated dry-run = zero delta
→ visual Roadmap confirmation
```

Инварианты операции:

- непустая дата не очищается и не перезаписывается неявно;
- задачи вне явно заявленного набора изменений сохраняют свои даты;
- новая задача не считается внесённой в календарный план без начала и
  завершения;
- до apply публикуется перечень карточек и полей, которые будут изменены;
- конфликт хотя бы одной карточки блокирует весь набор до первой мутации;
- изменение схемы или view не заменяет миграцию данных;
- lifecycle-sync статусов не имеет права менять плановые даты;
- после apply обе плановые пары должны совпадать, а повторный dry-run должен
  вернуть `items_repaired = 0` и `field_updates = 0`;
- если GitHub API не подтверждает визуальную раскладку, governance Issue
  остаётся открытой до ручной проверки владельцем проекта.

## Граница этапов

- Этап A: live-поля, новые фактические события, dry-run, представления.
- Этап B: отдельный dry-run исторического восстановления после `ATS-09B`.
- Этап A не придумывает плановые даты задним числом и не выполняет
  исторический backfill.
