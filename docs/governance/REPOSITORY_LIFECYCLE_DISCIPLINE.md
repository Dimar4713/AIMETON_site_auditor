# AIMETON Site Auditor — дисциплина жизненного цикла репозитория

## Статус

Нормативный локальный контракт. Дополняет `AIMETON_Project_Management_Policy.md` и `GITHUB_PROJECT_ROADMAP.md`. При расхождении применяется более строгое правило.

## 1. Основной принцип

Работа считается существующей только тогда, когда одновременно согласованы:

```text
Issue → Project status/dates → branch/PR → tests/CI → evidence → checklist → закрытие
```

Нельзя объявлять выполненным то, что не подтверждено наблюдаемым результатом. Нельзя скрывать невыполненное проставлением `[x]`, закрытием Issue или переносом статуса в Done.

## 2. Фактические даты

- `Actual start` фиксируется при первом исполнительном состоянии: `In Progress`, `In Review` или `Validation`.
- Для PR источником начала является исходный `created_at`; для Issue — доказуемое событие фактического исполнения.
- `Actual finish` фиксируется только при принятом завершении: merged PR, закрытая выполненная Issue или подтверждённый эквивалентный результат.
- `Actual finish` без `Actual start` запрещён.
- `Actual finish < Actual start` блокирует весь набор изменений fail-closed.
- Непустые фактические даты неизменяемы без отдельного доказанного исправления.
- `not_planned` и `duplicate` не считаются исполнением и не получают фиктивных фактических дат.

## 3. Issue и критерии приёмки

Каждая исполняемая Issue MUST содержать проверяемые критерии и секцию `Evidence of Done`.

- `[x]` означает только доказанно выполненный критерий.
- `[ ]` сохраняется, пока evidence недостаточно.
- Автоматическое изменение checklist разрешено только при однозначной связи с точным критерием.
- Неоднозначное соответствие всегда передаётся на ручное подтверждение.
- Родительская Initiative/Epic не закрывается по одному частичному PR; завершённые вертикальные срезы оформляются отдельными delivery-Issues.

## 4. Pull Request

Каждый технический PR MUST:

1. иметь явную связь `Part of`, `Closes`, `Fixes` или `Resolves #N`;
2. содержать непустую секцию `Acceptance criteria affected`;
3. перечислять проверки и наблюдаемый результат;
4. явно указывать оставшиеся разрывы;
5. не объявлять всю родительскую Issue завершённой при частичной реализации.

После merge автоматизация публикует evidence-комментарий в связанные Issues. Merge сам по себе не разрешает автоматически отмечать неоднозначные критерии.

## 5. Закрытие и Done

Issue нельзя оставить закрытой как `completed`, если в ней есть открытые обязательные критерии, кроме случая явного и допустимого переноса долга.

При нарушении автоматизация должна переоткрыть Issue или заблокировать переход.

Статус `Done` означает одновременно:

- реализация принята;
- тесты и CI зелёные;
- наблюдаемый результат подтверждён;
- фактические даты согласованы;
- checklist отражает evidence;
- документация и связанные планы обновлены;
- остаточный долг либо отсутствует, либо явно перенесён.

## 6. Debt transfer

`Debt transfer` не означает выполнение. Это явное принятие оставшегося обязательства.

Допустимый перенос MUST содержать:

- отдельную секцию `Debt transfer`;
- явную ссылку на открытую Issue `#N`;
- описание переносимого обязательства;
- причину, почему оно не закрывается в текущей Issue;
- владельца/контур дальнейшего погашения.

Пустая секция, ссылка на закрытую нерелевантную карточку или общий текст без Issue-ссылки не скрывают нарушение.

Перенос не может скрывать нарушения фактических дат.

## 7. Массовые изменения и ремонт Project

Любой backfill, migration или repair MUST выполнять последовательность:

```text
read-only inventory → snapshot → dry-run → exact allowlist → conflict gate
→ protected apply → read-back → repeated dry-run → zero delta
```

Запрещены:

- запись до полного preflight;
- расширение набора «по ходу»;
- перезапись непустых значений;
- вывод даты из удобного, но недоказанного timestamp;
- автоматическое разрешение конфликта;
- заявление успеха без read-back.

## 8. Аудит

Нормативные результаты аудита:

- `PASS` — скрытых нарушений и зарегистрированного долга нет;
- `PASS WITH TRACKED DEBT` — скрытых нарушений нет, долг явно зарегистрирован и управляется;
- `FAIL` — есть нарушение инварианта или скрытый долг;
- `INCONCLUSIVE` — проверка не получила достаточного evidence.

`PASS WITH TRACKED DEBT` не закрывает реестр долга. Он подтверждает дисциплинированное управление исключениями.

## 9. Fail-closed

При конфликте данных, отсутствующем evidence, неоднозначном соответствии, неизвестном lifecycle или ошибке read-back система останавливается до мутаций либо не признаёт завершение.

Удобство, срочность и зелёный отдельный workflow не заменяют доказательство полного контура.

## 10. Межрепозиторная синхронизация

Общесистемный урок или инвариант MUST быть поднят в `aimeton-architecture`. Локальная автоматизация без нормативной фиксации не считается полностью интегрированным улучшением AIMETON.
