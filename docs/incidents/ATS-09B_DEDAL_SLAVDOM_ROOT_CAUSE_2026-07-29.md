# ATS-09B: причины поверхностного анализа dedal24.ru и slavdom24.ru

Дата разбора: 2026-07-29.

## Итог

Два запуска считаются не «сайтами с малым количеством данных», а провалом
аналитического контура. Открытые данные существовали, но система не довела их
от обнаружения до проверенных claims и всё равно разрешила пользовательский
экспорт.

## Подтверждённая причинная цепочка

1. `/api/analyze` загружал только переданный URL. Обход внутренних страниц,
   `sitemap`, контактов, реквизитов, доставки, оплаты, филиалов и каталога не
   выполнялся.
2. Поисковое имя компании выводилось из заголовка страницы простым разделением
   по `—` и `|`. Для товарных заголовков запрос мог строиться по общей фразе, а
   не по бренду или юридическому лицу.
3. Результаты SearXNG оставались `discovery_hint` и snippets. Первичные
   документы по найденным URL не загружались, не проверялись и потому не
   становились доказательствами.
4. Ошибка Pydantic `ValidationError` отбрасывала полный ответ модели. После неё
   запуск сразу переходил в `heuristic_analysis`, которому передавался текст
   одной страницы без сохранённого набора внешних источников.
5. Старый UI/PDF не показывал значимую часть уже структурированных полей:
   `company_facts`, `sources` и `business_machine_4x4`. Общий чат дополнительно
   попадал в PDF и мог переносить контекст другой компании.

## Почему результат выглядел убедительнее, чем был

- приоритетные оценки не были ограничены полнотой профиля и качеством
  доказательств;
- `degraded` и fallback не блокировали клиентский экспорт;
- количество оформленных страниц скрывало малое число уникальных фактов;
- PDF был снимком интерфейса, а не представлением подписанного Report v1.

## P0-критерии исправления

- изоляция UI и экспорта по `analysis_id`;
- запрет чата и другого домена в клиентском файле;
- fail-closed при `ValidationError` и деградации обязательных вертикалей;
- entity resolution: бренд → домен → контакты → ИП/ООО → связанные компании;
- доменный обход обязательных внутренних страниц;
- загрузка и проверка первичных документов из discovery results;
- JSON repair/retry до перехода в fallback;
- fallback сохраняет найденные источники и не маскируется как полный анализ;
- отдельные оценки коммерческого приоритета, полноты профиля и доказательности.

## Состояние купирования SA-SR-00

Фактическое состояние draft-ветки PR #79 после начала SA-SR-00:

- неподписанные JSON/MD/DOCX остаются предварительными и всегда имеют
  `client_release_eligible=false`;
- эвристический fallback получает состояние `preliminary_hypothesis`;
- введён обязательный `MissionReleaseControl`, связанный отдельным digest с
  human sign-off;
- Report Gate блокирует `ValidationError`, `degraded`,
  `identity_unresolved`, критический конфликт, УДП ниже L4, незавершённую
  обязательную вертикаль, неготовый обязательный provider и неизвестный либо
  исчерпанный budget;
- УДП, полнота профиля, качество evidence и коммерческий приоритет выводятся
  раздельно;
- отсутствие release-control snapshot закрывает review-package до выпуска.

Это купирует ложнополный клиентский выпуск, но не исправляет сам поиск.
Фактическое восстановление входных данных, mission loop, identity resolution,
crawler и УДП выполняется последующими задачами #82–#86. До merge PR, зелёного
CI и развёртывания stage это состояние является реализованным в ветке, но не
эксплуатационным фактом.

## Обязательная регрессия

После реализации P0 повторно запустить:

- `https://dedal24.ru/`;
- `https://www.slavdom24.ru/`.

Успех допускается только при отсутствии межаналитического загрязнения,
сформированном юридическом профиле, проверенных внутренних страницах,
явной оценке полноты и доказательств и выпуске через Report v1.
